EXPT 1 · DDL & DML COMMANDS

Defining structure, then filling it in.

DDL (Data Definition Language) shapes the database and its tables. DML (Data Manipulation Language) adds, changes, and removes the data inside them. DDL statements auto-commit in MySQL; DML statements don't, until you COMMIT.

DDL commands

CommandPurposeSyntaxExample
CREATE DATABASECreates a new databaseCREATE DATABASE db_name;CREATE DATABASE College;
USESelects a database to work inUSE db_name;USE College;
CREATE TABLECreates a new tableCREATE TABLE t (col type, ...);CREATE TABLE Student (RollNo INT, Name VARCHAR(20), Age INT);
SHOW TABLESLists all tables in a DBSHOW TABLES;—
DESCShows a table's structureDESC t;DESC Student;
ALTER ... ADDAdds a new columnALTER TABLE t ADD col type;ALTER TABLE Student ADD Email VARCHAR(30);
ALTER ... MODIFYChanges a column's datatypeALTER TABLE t MODIFY col type;ALTER TABLE Student MODIFY Name VARCHAR(40);
ALTER ... DROPRemoves a columnALTER TABLE t DROP col;ALTER TABLE Student DROP Age;
RENAME TABLERenames a tableRENAME TABLE old TO new;RENAME TABLE Student TO Student_Details;
TRUNCATE TABLEDeletes all records, keeps structureTRUNCATE TABLE t;TRUNCATE TABLE Student_Details;
DROP TABLEDeletes a table entirelyDROP TABLE t;DROP TABLE Student_Details;
DROP DATABASEDeletes a database entirelyDROP DATABASE db;DROP DATABASE College;

DML commands

CommandPurposeSyntaxExample
INSERT (full row)Adds a new record with all columnsINSERT INTO t VALUES (...);INSERT INTO Student VALUES (1, 'Arun', 20);
INSERT (selected cols)Adds a record for specific columns onlyINSERT INTO t (c1, c2) VALUES (...);INSERT INTO Student (RollNo, Name) VALUES (2, 'Kumar');
UPDATEModifies existing recordsUPDATE t SET col=val WHERE cond;UPDATE Student SET Age=21 WHERE RollNo=1;
DELETERemoves matching recordsDELETE FROM t WHERE cond;DELETE FROM Student WHERE RollNo=2;
VIVA POINTDELETE removes rows and can be rolled back (DML, logged row-by-row); TRUNCATE removes all rows fast and resets identity, but is DDL-like and can't be rolled back in most engines; DROP removes the table structure itself. Always know which one a question is really asking about.

EXPT 3B · ENTITY-RELATIONSHIP DIAGRAM

Modeling the data before you build the tables.

An ER diagram is a visual model of entities, their attributes, and how they relate — drawn before any table is created.

Components

  • Entity — strong (independently identifiable) or weak (depends on a strong entity for identity)
  • Attribute — key, composite, multivalued, or derived
  • Relationship — one-to-one, one-to-many, many-to-one, many-to-many

Shapes and their meaning

ShapeRepresentsDefinition
RectangleEntityA real-world object with independent existence, uniquely identifiable.
Double rectangleWeak entityCannot be uniquely identified by its own attributes; depends on a strong entity.
EllipseAttributeA property describing an entity or relationship.
Ellipse, underlinedKey attributeUniquely identifies an entity (e.g. RollNo).
Ellipse of ellipsesComposite attributeCan be split into smaller sub-attributes (e.g. Address → Pin, State, Country).
Double ellipseMultivalued attributeCan hold more than one value for a single entity (e.g. Stu_Phone).
Dashed ellipseDerived attributeCalculated from other attributes (e.g. Age from date_of_birth).
DiamondRelationshipAn association between two or more entities.
Double diamondIdentifying relationshipConnects a weak entity to its owner entity.
LineConnectorLinks attributes to entities, and entities to relationships.
Double lineTotal participationEvery entity instance must participate in the relationship.

Cardinalities

CardinalityMeaningExample
One to One (1:1)One entity relates to exactly one in another setPerson – has – Passport
One to Many (1:M)One entity relates to many in another setCustomer – placed – Order
Many to One (M:1)Many entities relate to one in another setStudent – Study – College
Many to Many (M:N)Many relate to manyStudent – Assigned – Project

Extended features

  • Overlapping specialization/generalization — an entity from a superclass can belong to more than one subclass at once.
  • Disjoint specialization/generalization — an entity can belong to only one subclass at a time.
  • Aggregation — a relationship set is treated as a higher-level entity set, so it can itself take part in another relationship.

Worked example (from the workbook): Student (Register Number, Name, Dept, Semester) — Enrolls (M:N) — Course (Faculty ID, Code, Title, Date); Faculty (Faculty ID, Name, Mobile No [derived], Location) — Teach — Course, and Faculty — Mentor — Student.

VIVA POINTA weak entity has no key of its own strong enough to identify it alone — it borrows the strong entity's key plus a partial key of its own, connected via an identifying relationship (double diamond).

EXPT 6 · PL/SQL — PROCEDURES, FUNCTIONS, CURSORS, TRIGGERS, EXCEPTIONS

Programs that live inside the database.

Procedures

DELIMITER $$ CREATE PROCEDURE procedure_name () BEGIN statements; END$$ DELIMITER ;

Called with CALL procedure_name();. Example: update_salary(IN p_emp_id INT, IN p_new_salary INT) runs UPDATE employee SET salary=p_new_salary WHERE emp_id=p_emp_id;

Functions

DELIMITER $$ CREATE FUNCTION function_name (parameter datatype) RETURNS datatype DETERMINISTIC BEGIN RETURN value; END$$ DELIMITER ;

A function always returns a value and can be used inline in a SELECT — e.g. SELECT emp_id, salary, calculate_bonus(salary) AS bonus FROM employee; — which a procedure cannot do.

Cursors

A cursor processes a multi-row query result one row at a time; used only inside stored procedures. Implicit cursors are created automatically for INSERT/UPDATE/DELETE; explicit cursors are declared by the programmer for a SELECT returning multiple rows. Lifecycle: Declare → Open → Fetch → Close.

DECLARE cursor_name CURSOR FOR SELECT_statement; DECLARE CONTINUE HANDLER FOR NOT FOUND SET done = 1; OPEN cursor_name; read_loop: LOOP FETCH cursor_name INTO variables; IF done = 1 THEN LEAVE read_loop; END IF; -- process row END LOOP; CLOSE cursor_name;

Triggers

A trigger auto-executes on a table event. Events: INSERT, UPDATE, DELETE. Types: BEFORE (runs before the change), AFTER (runs after), and row-level (default — runs once per affected row). MySQL allows only one event per trigger.

DELIMITER $$ CREATE TRIGGER trigger_name BEFORE | AFTER INSERT | UPDATE | DELETE ON table_name FOR EACH ROW BEGIN trigger_body; END$$ DELIMITER ;

Example 1 (BEFORE INSERT): clamps any new salary below 10000 up to 10000 using SET NEW.salary = 10000;

Example 2 (AFTER UPDATE, audit log): writes OLD.salary, NEW.salary, and NOW() into a salary_log table whenever salary changes.

Exception handling

Lets a program handle runtime errors gracefully instead of terminating abruptly.

Handler typeBehaviour
CONTINUEContinues execution after handling the error
EXITExits the block after handling the error
ConditionFires on
NOT FOUNDCursor fetch reaches the end
SQLEXCEPTIONAny SQL error
SQLWARNINGA SQL warning
Error codeA specific error number, e.g. 1062 (duplicate key)

Worked example: DECLARE EXIT HANDLER FOR SQLEXCEPTION catches a duplicate-key insert into a student table and returns "Error: Duplicate ID or SQL Error" instead of crashing the procedure.

VIVA POINTFunction vs procedure, one line: a function must return exactly one value and can be used inside a SELECT expression; a procedure may return nothing (or multiple result sets/OUT params) and is invoked with CALL, not embedded in a query.

EXPT 7A · NORMALIZATION — 1NF, 2NF, 3NF

Removing redundancy, one dependency at a time.

Normalization reduces redundancy and eliminates update/insertion/deletion anomalies by splitting large tables into smaller, well-structured ones, following a sequence of normal forms.

1NF — First Normal Form

Every field holds an atomic (indivisible) value — no multi-valued attributes, no repeating groups.

Violation example: a Subjects column holding "DBMS, OS" for one student. Fix: split into one row per (StudentID, Subject) pair.

2NF — Second Normal Form

Already in 1NF, and no partial dependency — every non-key attribute depends on the whole composite primary key, not just part of it. Only relevant when the primary key is composite.

Violation example: ORDER(OrderID, ProductID, CustomerName, Price) with key (OrderID, ProductID) — CustomerName depends only on OrderID, Price depends only on ProductID. Fix: split into ORDER(OrderID, CustomerName), PRODUCT(ProductID, Price), and a junction table ORDER_PRODUCT(OrderID, ProductID).

3NF — Third Normal Form

Already in 2NF, and no transitive dependency — a non-key attribute must not depend on another non-key attribute.

Violation example: EMPLOYEE(EmpID, EmpName, DeptName, DeptLocation) — DeptLocation depends on DeptName, which depends on EmpID (EmpID → DeptName → DeptLocation). Fix: split into EMPLOYEE(EmpID, EmpName, DeptName) and DEPARTMENT(DeptName, DeptLocation).

VIVA POINTPartial dependency needs a composite key to even exist (2NF); transitive dependency is about a chain between two non-key attributes (3NF) — mixing these two up is the single most common viva slip.

EXPT 7B · NORMALIZATION — 4NF, 5NF

Beyond 3NF — multi-valued and join dependencies.

4NF — Fourth Normal Form

Already in BCNF, and no non-trivial multi-valued dependency (MVD) — one attribute determining multiple independent values of another, unrelated attribute.

Violation example: EMP_SKILL_PROJECT(EmpID, Skill, Project) where an employee's skills and projects vary independently of each other (EmpID →→ Skill, EmpID →→ Project) — every combination of skill × project gets repeated. Fix: split into EMP_SKILL(EmpID, Skill) and EMP_PROJECT(EmpID, Project).

5NF — Fifth Normal Form (Project-Join Normal Form)

Already in 4NF, with no join dependency — the table can't be losslessly reconstructed from smaller decomposed tables, so it can't be broken down any further without losing information.

Violation example: SUPPLIER_PART_PROJECT(Supplier, Part, Project), where the relationship only holds when all three attributes are combined together. Fix: split into SUPPLIER_PART(Supplier, Part), SUPPLIER_PROJECT(Supplier, Project), and PART_PROJECT(Part, Project) — the original table is recoverable only by joining all three back together.

VIVA POINTOften asked alongside this pair: BCNF (Boyce-Codd Normal Form) sits between 3NF and 4NF — a table is in BCNF if, for every functional dependency X→Y, X is a superkey. It's a stricter version of 3NF that closes a loophole 3NF leaves open when a table has multiple overlapping candidate keys.

EXPT 8 · TRANSACTIONS & CONCURRENCY CONTROL

Keeping data correct when many things happen at once.

Transaction control

CommandPurpose
START TRANSACTION / BEGINStarts a transaction block; changes aren't permanent yet
COMMITPermanently saves all changes in the transaction
ROLLBACKUndoes all changes in the current transaction
SAVEPOINTMarks a point within a transaction to roll back to

RELEASE SAVEPOINTDeletes a savepoint that's no longer needed
BEGIN; INSERT INTO account VALUES (101, 'Asha', 5000); SAVEPOINT sp1; UPDATE account SET balance = balance - 1000 WHERE acc_no = 101; ROLLBACK TO sp1; COMMIT;

Concurrency control — locks

Lock typePurposeEffect
Shared Lock (READ)Many transactions can read, none can writeLOCK TABLES account READ; — SELECT allowed, writes blocked
Exclusive Lock (WRITE)Only one transaction can read or writeLOCK TABLES account WRITE; — all others blocked
Row-Level LockLocks only the needed rowSELECT * FROM account WHERE acc_no=101 FOR UPDATE; — other rows stay accessible
Table-Level LockLocks the whole tableEntire table unavailable to others until released
Predicate Lock (SERIALIZABLE)Prevents phantom reads under the strictest isolation levelA second transaction inserting a row matching the first's WHERE clause is blocked

Isolation levels, low to high strictness: Read Uncommitted (allows dirty reads) → Read Committed (blocks dirty reads) → Repeatable Read (blocks dirty + non-repeatable reads) → Serializable (also blocks phantom reads, at the cost of concurrency).

VIVA POINTThree classic anomalies: a dirty read sees another transaction's uncommitted change; a non-repeatable read gets a different value re-reading the same row mid-transaction; a phantom read sees new rows appear that match a repeated query's condition. Each stricter isolation level blocks one more of these, at the cost of concurrency.

EXPT 9 · DATABASE CONNECTIVITY WITH FRONT-END TOOLS

Getting user input into the database and back out.

The general flow, independent of stack: user submits a form → server-side script receives it → driver connects to the DB → query executes → result returns to the front end.

Steps involved

  1. Load the driver — e.g. mysql-connector (Python), mysql (Node.js), JDBC (Java).
  2. Provide connection details — host, database name, username, password.
  3. Establish the connection using the driver.
  4. Select the database to work with.
  5. Create a statement/cursor object to send SQL commands.
  6. Select the target table.
  7. Execute the SQL query — INSERT, SELECT, UPDATE, DELETE.
  8. Process the result — rows retrieved, or execution status.
  9. Commit or rollback the transaction.
  10. Close the connection to release resources.
  11. Return the result to the server, then display it on the front end.

Minimal example (Python/Flask)

db = mysql.connector.connect(host="localhost", user="root", password="", database="bankdb") cursor = db.cursor() @app.route('/insert', methods=['POST']) def insert(): acc_no = request.form['acc_no'] name = request.form['name'] balance = request.form['balance'] sql = "INSERT INTO account VALUES (%s, %s, %s)" cursor.execute(sql, (acc_no, name, balance)) db.commit() return "Record inserted successfully"

The same pattern repeats in Node.js (mysql.createConnection + db.query) and Java (JDBC's DriverManager.getConnection + PreparedStatement).

VIVA POINTAlways use parameterized queries / prepared statements (the %s / ? placeholders above) instead of string-concatenating user input into SQL — that's what prevents SQL injection.
