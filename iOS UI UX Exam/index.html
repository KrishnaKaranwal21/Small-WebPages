Class 1 · Principles of UX/UI

UI vs UX

  • UI = what the user sees and interacts with (layout, typography, buttons, colours, icons, controls). Focus: presentation and interaction surface.
  • UX = the overall experience of achieving a goal (needs, tasks, flow, usability, accessibility, satisfaction). Focus: usefulness, ease, outcomes.
  • Car analogy: UI = steering wheel/dashboard; UX = the whole drive. Good UI helps UX, but pretty screens alone don’t guarantee good UX.
  • UI is 90% perception; UX is 90% behaviour → design is 90% human psychology.
  • Bad design costs: wasted effort, errors and rework, lost trust.

7 criteria of a successful interface

Useful · Clear · Consistent · Efficient · Feedback-rich · Accessible · Pleasant

4 working principles

  • Clarity – make the next action obvious; one primary action per screen; label by what it does.
  • Consistency – reduce the need to relearn; similar things look, are labelled and behave similarly.
  • Feedback – users should know what is happening; “Silence is the most common usability failure.” States: Selected, Saved, Loading, Completed, Unavailable.
  • User Control – prevent errors, then support recovery. Prevent: constrain invalid actions, defaults, clarify destructive actions, confirm only when necessary. Recover: Undo, preserve input, explain, show next action.

Users, tasks, usability

  • Design starts with the user (who, what they know, device/context, constraints) and the task (goal, info, steps, where error occurs).
  • Usability dimensions: Learnability, Efficiency, Memorability, Error tolerance, Satisfaction.
  • Vocabulary: Goal (what they want) · Task (work required) · Journey (sequence of interactions/decisions) · Pain point (effort/confusion/failure rises) · Opportunity (change that reduces friction).
  • Evaluation framework (6): Goal, Path, Clarity, Consistency, Feedback, Recovery.
  • Worked example: Open app → Choose service → Select date → Select time → Confirm. Pain points: unclear availability, hidden fees, lost selections, no confirmation.

Class 2 · Evaluating Interactive Design

Evaluator’s mindset

  • Don’t ask “Do I like it?” Ask: can the user accomplish the goal, understand what to do, do it efficiently, recover from mistakes, and know what happened? Evaluate from the user’s point of view.
  • 5 usability dimensions: Effectiveness (complete the task?) · Efficiency (effort?) · Learnability (new user can understand?) · Error Tolerance (prevent/recover?) · Satisfaction (understandable, manageable?).
  • Evaluation loop: Goal → Task → Observe → Identify → Improve → Test. (Journey: Principles → Observe → Identify → Improve → Test.)

5 UX review roles

  • User – who am I, goal, expectations, confidence/confusion.
  • Task Analyst – steps, order, unnecessary steps, efficiency.
  • UX Observer – friction: hesitation, confusion, uncertainty, errors, unnecessary thinking, missing info.
  • UI Analyst – layout, hierarchy, buttons, labels, navigation, typography, spacing, consistency.
  • UX Researcher – impact: how serious, how often, affects main task?, recoverable?, most valuable improvement.
  • Team deliverable: 5 role findings + 3 things that work, 3 important problems, 3 improvements. Don’t repeat the same observation across roles.

Heuristic evaluation

  • Systematic inspection using established usability principles. Instead of “something feels wrong” ask “which principle is violated?” Structured, early, finds common problems fast — but doesn’t replace testing with real users.
  • 10 heuristics (questions): system status visible · familiar language · control & undo · consistency · error prevention · recognition over recall · efficient use · remove unnecessary info · understand & recover from errors · useful help.
  • Visibility: Save → “Saved”; Upload → “65% complete”; Payment → “successful”; Delete → “moved to Trash”.
  • Recognition beats recall: show “Selected: Chennai → Singapore” instead of making users remember.
  • Error flow: Prevent → Detect → Explain → Recover. Prevent = defaults, validation, constrained choices, clear destructive actions. Recover = undo, preserve info, explain, next action.

Describing problems, tasks, severity

  • Weak: “Looks bad.” Better: names the issue. Strong: what happened → why it matters → what could improve.
  • Observation → Problem → Impact → Improvement (taps twice → no visible response → thinks first tap failed → give immediate feedback).
  • Task-based evaluation: pick a real task (e.g., book a doctor’s appointment); examine actions, hesitation, mistakes, backtracking, goal reached.
  • Watch behaviour: Hesitation, Error, Backtracking, Question, Workaround (invents another way), Abandonment (stops before completing).
  • Severity factors: Frequency, Impact, Reach, Recovery. High impact + high frequency = high priority. Blocked checkout > small visual issue.
  • Comparing alternatives (same task, not taste): Clarity, Efficiency, Consistency, Feedback, Error prevention, Recovery.
  • Critique: critique the design, not the designer. Good feedback = Specific, Evidence-based, Actionable, Respectful.
  • Presentation: 5 speakers × 30 s = 2 min 30 s per team; answer What? Why? So what? What should change?

Class 3 · Design Fundamentals (Building a Design)

Five building blocks

BlockRoleKey points
LayoutWhere things go / organisesPosition, alignment, grouping, balance, flow. Grid = hidden skeleton (columns, margins, gutters, consistent widths). Alignment creates invisible relationships.
TypographyHow words speak / communicatesNot decoration – information architecture: communicate, organise, emphasise, set tone, support scanning.
ColourWhat attracts and signalsAttract attention, group, show state, emphasise, set mood.
HierarchyWhat matters first / prioritisesSize, weight, colour, order, spacing; one clear primary action.
SpacingWhat creates rhythm / breathesSeparates, groups, rhythm, scanning, lowers cognitive load.

Together they create Visual Clarity. Class 3 recaps: UI = Perception, UX = Psychology; four principles (Clarity, Consistency, Feedback, User Control).

Details to memorise

  • Visual flow (5): Scan → Orient → Read → Decide → Act.
  • Layout structure (mobile): top banner, content cards, quick action, bottom navigation, consistent spacing. Navigation always accessible and consistent across screens.
  • Type scale: Display 64px (biggest statement) · Heading 32px (major section) · Body 16px (main info) · Caption 14px (supporting). H1 48px, button 16px.
  • Legibility (can I recognise characters?): typeface, letterforms, size, weight. Readability (can I comfortably read content?): line length, line height, spacing, contrast.
  • Choose type with purpose: product personality, language support, small-size behaviour, enough weights, read quickly. Inter = modern & clean; Roboto = friendly & neutral; Merriweather = traditional & elegant.
  • Colour system: Primary #2563EB, Secondary #EC4899, Accent #F59E0B; Neutrals (text #0F172A, secondary #64748B, border #E2E8F0, bg #F8FAFC); Semantic: Success #10B981, Error #EF4444, Warning #F59E0B, Info #3B82F6. Keep it simple, consistent, accessible, good contrast.
  • Information hierarchy (top→bottom): top level (greeting, notifications, profile) → hero banner → core features → secondary content → bottom navigation.
  • Hierarchy tools: larger for key elements, bolder for primary actions, clear order, subtle for secondary details; consistent sizes for similar elements.
  • One screen, one story: one obvious goal, everything supports it, make the next action easy.
  • Spacing system: repeatable 8-based scale (8, 16, 24, 32, 48, 64). “Consistency beats random spacing.” “Spacing is not empty. Spacing is structure.”
  • Class 3 challenge: redesign one screen — fix layout, establish typography, build colour system, create hierarchy, add consistent spacing.

Class 4 · Interaction Design

Core ideas

  • Interaction design = how users and products behave with each other. Asks: what can the user do? what happens when they act? how does the system respond? what does the user understand? what next?
  • Visual design = layout, typography, colour, hierarchy, spacing. Interaction design = action, response, feedback, state, flow.
  • Interaction loop: User action → System response → User understands → Next action.
  • Affordance = communicates what an element lets you do without explanation (button looks tappable, link clickable, text field editable, drag handle = movement, slider = adjustment).
  • Feedback – “Did it work?”: Tap → pressed state; Save → success message; Load → progress indicator; Delete → confirmation; Submit → result.
  • States (button family of 8): Default, Hover, Pressed, Focused, Disabled, Loading (“Saving…”), Success (“Saved ✓”), Error (“Retry”). Design the states, not just the component. Ask: what should the button communicate at every moment?

Navigation, forms, errors

  • Journey: Home → Category → Detail → Action → Confirmation. After every action: does the user know what to do next?
  • Patterns: Tabs (switch related sections) · Bottom nav (primary areas) · Back (return to previous context) · Breadcrumbs (understand location) · Search (find known target) · Progress indicators (multi-step task). Choose by the user’s task, not preference.
  • Form parts: Label (what is this?) · Input (where do I type?) · Hint (format?) · Validation (valid?) · Error (how to fix?). Forms are conversations; reduce uncertainty.
  • High friction: too many fields, unclear labels, poor defaults, validation only after submit, repeated info. Low friction: clear labels, smart defaults, inline validation, suggestions, only necessary fields.
  • Error handling: Prevent → Explain → Guide → Recover. Bad: “Payment failed.” Good: “Your card has expired. [Update Card]” (explains, guides, recovers).

Micro-interactions, motion, loading, empty states, lifecycle

  • Micro-interactions: Toggle → state changed; Like → action registered; Copy → content copied; Toast → status communicated; Spinner → work in progress; Animation → change explained. Small things → large gains in perceived quality.
  • Motion explains, not decorates: where something came from, went, what changed, opened, closed, what belongs together.
  • Loading: no feedback (“Is it working?”) → spinner (“Something is happening”) → progress (“how far we are”) → time estimate (“what to expect”). Uncertainty creates frustration; feedback creates confidence.
  • Empty state (“Nothing is still a state”): explain the situation, give context, suggest next action (“You have no saved projects yet. [Create Project]”). Weak: “No data.”
  • Lifecycle: Default → Interaction → Loading → Success → Error. “Don’t design a screen. Design what the screen becomes.”
  • User flow: Enter → Browse → Choose → Confirm → Complete; Goal → Flow → Action → Outcome.
  • 5 questions of a complete interaction: What can I do? What will happen? Did it work? What happens next? What if I make a mistake?
  • 5 Fundamentals: Affordance (what can I do?) · Feedback (did it work?) · States (what is happening?) · Flow (where do I go?) · Recovery (what if it fails?). “Clarity of behaviour creates confidence.”
  • Checklist: actionable clear? every action has feedback? states designed? navigation preserves context? recover from errors? next action obvious?
Exam tip: MCQs usually test (1) law/term → definition matching, (2) “which is NOT part of…”, (3) scenario → principle. Learn the lists in order and their one-line meanings.
